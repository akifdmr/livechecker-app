# S1 — Existing schema mapping and additive migration

Follow the repository AGENTS.md payment rules. Preserve the current schema and
use provider-hosted checkout or tokenization. Never introduce PAN/CVV storage,
raw-card checks, or raw provider response storage.

Existing equivalents to reuse:
- `users.role` already exists; `setup-db.js` creates the admin from
  `ADMIN_EMAIL` and `ADMIN_PASSWORD` environment variables.
- `bin_checks` already exists.
- `card_enrollments` is the payment-method table and stores provider-issued
  references only; do not add a parallel `cards` table.
- `processor_accounts` stores encrypted per-user processor credentials;
  `processor_routing` stores routing. Do not create a second provider-secret
  store or seed credentials/provider accounts.
- `merchant_transactions` and `charges` already store transaction metadata.
- `audit_events` and `charge_audit` already provide audit history.

Add only missing, safe schema:
- `users.credits`, initialized to zero.
- `credit_ledger` with owner, amount, resulting balance, reference and
  idempotency fields; no payment credentials or card data.
- `settings` for non-secret settings only; leave unconfigured values unset.
- `provisions` linked to an existing `card_enrollments` row, with provider
  transaction reference/status/amount only. No PAN, CVV, payment token, or
  authentication secret columns.

Use an additive migration and indexes for owner, status, and provider
transaction reference. Do not seed guessed fee amounts, default authorization
amounts, max-failure values, or active providers. Keep admin setup environment
based and document `npm run migrate` plus `npm run setup` instructions. Do not
run a destructive reset or a migration against a live database.

Completion format:
DONE
- paths: changed files
- reused: existing schema/services
- run: migration/setup commands (state clearly if not executed)
- risk: remaining configuration or limitations
